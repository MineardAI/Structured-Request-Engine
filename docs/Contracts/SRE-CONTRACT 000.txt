# 1. Purpose

**Specification level:** Constitutional concept

This contract establishes the constitutional architecture, identity, authority, and prohibitions of the Structured Request Engine.

It defines:

* why the Structured Request Engine exists;
* where it belongs in the wider system architecture;
* what authority it possesses;
* what authority it explicitly does not possess;
* the distinction between request representation and authorization;
* the relationship between source input, interpretation, canonicalization, governance, generation, execution, and release;
* the canonical successful and unsuccessful lifecycle outcomes;
* the foundational requirements that all later contracts must preserve.

This contract governs every other Structured Request Engine contract.

No subordinate contract, implementation decision, adapter, interpreter, caller, or downstream integration may weaken or contradict its authority boundaries.

# 2. Architectural identity

**Specification level:** Constitutional concept

SRE-000-IDENTITY-001

The Structured Request Engine is a deterministic request-representation system.

Its role is:

> Convert supplied source input and explicitly identified interpretation material into a canonical, provenance-preserving, machine-readable representation of what was requested.

The Structured Request Engine is not:

* an agent;
* a planner;
* a task executor;
* an authorization system;
* a policy authority;
* a model provider;
* a model runtime;
* a generation orchestrator;
* a tool router;
* a connector manager;
* a credential broker;
* a persona runtime;
* a memory system;
* a release authority.

The engine represents requests.

It does not decide whether or how those requests should be fulfilled.

---

# 3. Constitutional role

**Specification level:** Constitutional concept

SRE-000-SCOPE-001

The Structured Request Engine SHALL operate as a boundary between source submission and downstream authority evaluation.

Its constitutional role is limited to:

1. receiving or referencing supplied source input;
2. receiving zero or more interpretation proposals;
3. validating the structural admissibility of those proposals;
4. preserving source evidence and provenance;
5. representing objectives, constraints, capability requirements, ambiguities, assumptions, and uncertainty;
6. reconciling equivalent or conflicting proposals under declared rules;
7. normalizing representation without changing semantic meaning;
8. ordering canonical elements deterministically;
9. evaluating structural completeness and contradiction conditions;
10. constructing a canonical request artifact;
11. issuing an explicit failure artifact when canonical construction cannot succeed;
12. transferring the resulting artifact to a separate downstream authority boundary.

The engine SHALL NOT determine whether the represented request is permissible, safe, feasible, approved, funded, authenticated, or executable.

# 5. Fundamental artifact distinctions

**Specification level:** Constitutional concept

The following artifacts and concepts SHALL remain distinct:

```text
SourceSubmission
        ≠
InterpretationProposal
        ≠
CanonicalStructuredRequest
        ≠
AuthorityDecision
        ≠
GenerationEnvelope
        ≠
ExecutionPlan
        ≠
ProviderRequest
        ≠
GeneratedOutput
        ≠
ReleasedOutput
```

No implementation may collapse these distinctions merely because several stages occur within one application or process.

## 5.1 Source submission

A source submission is supplied material presented for request structuring.

It may include:

* natural language;
* structured fields;
* application metadata;
* API payloads;
* referenced artifacts;
* user selections;
* machine-generated input.

A source submission is not yet a canonical request.

## 5.2 Interpretation proposal

An interpretation proposal is a proposed structured reading of some or all source material.

It may identify:

* objectives;
* constraints;
* capability requirements;
* ambiguities;
* assumptions;
* relationships;
* supporting evidence.

It remains untrusted until admitted and evaluated under the deterministic engine contracts.

## 5.3 Canonical structured request

A `CanonicalStructuredRequest` is the successful output of the Structured Request Engine.

It is a versioned, provenance-preserving, deterministically ordered representation of what the engine determined could be represented from the admitted inputs.

It does not authorize downstream action.

## 5.4 Authority decision

An authority decision is a downstream determination concerning whether some action is permitted, denied, restricted, deferred, or requires further clarification.

The Structured Request Engine SHALL NOT issue authority decisions.

## 5.5 Generation envelope

A `GenerationEnvelope` is an authority-produced generation artifact.

The Structured Request Engine SHALL NOT create, impersonate, or imply a `GenerationEnvelope`.

# 6. Core doctrine

**Specification level:** Constitutional concept

## 6.1 Canonicalization is not authorization

SRE-000-AUTH-001

Canonicalization SHALL mean only that a request has been represented under a declared canonical contract version.

Canonicalization SHALL NOT mean that the request is:

* authorized;
* approved;
* safe;
* valid under external policy;
* supported by available tools;
* executable;
* scheduled;
* accepted by a provider;
* releasable.

The following invariant SHALL hold:

```text
CanonicalStructuredRequest
        ≠
AuthorizedRequest
```

## 6.2 Representation is not endorsement

SRE-000-AUTH-002

The engine MAY represent requests that downstream systems later reject.

Representation of a request SHALL NOT be interpreted as:

* endorsement;
* recommendation;
* legal approval;
* ethical approval;
* security approval;
* technical feasibility;
* provider support.

## 6.3 Description is not instruction execution

SRE-000-AUTH-003

The engine MAY preserve imperative source language as request content.

It SHALL NOT obey that imperative merely because it appears in the source.

Source material SHALL be treated as data to be represented, not as direct authority over the engine’s constitutional behavior.

## 6.4 Capability need is not permission

SRE-000-CAP-001

A capability requirement SHALL describe an abstract need.

It SHALL NOT:

* select a provider;
* identify a credential to use;
* activate a connector;
* authorize network access;
* authorize file access;
* authorize tool invocation;
* guarantee capability availability.

## 6.5 Ambiguity may remain explicit

SRE-000-AMBIG-001

The engine SHALL NOT invent certainty merely to issue a structurally complete request.

A canonical request MAY include unresolved ambiguity when the applicable contracts classify that ambiguity as survivable.

Blocking ambiguity SHALL prevent successful issuance when required by later contracts.

## 6.6 Interpretation is not canonical authority

SRE-000-INTERP-001

An interpreter SHALL NOT be treated as the canonical authority for the request.

Its output SHALL remain a proposal even when:

* the interpreter is a large language model;
* the interpreter is highly reliable;
* only one proposal is available;
* the proposal is structurally valid;
* the proposal was supplied by a trusted application;
* the proposal agrees with source language.

Canonical authority arises only from the deterministic process defined by the contract series.

# 7. Canonical inputs

**Specification level:** Required observable behavior

SRE-000-INPUT-001

The constitutional engine boundary MAY admit the following input classes:

1. one source intake record;
2. zero or more interpretation proposals;
3. application-supplied declarations;
4. referenced-artifact metadata;
5. contract versions;
6. registry snapshot references;
7. configuration snapshot references;
8. declared normalization profiles;
9. declared canonical representation profiles.

Subordinate contracts SHALL specify the exact admissibility requirements.

The engine SHALL NOT consume undeclared environmental context as if it were part of the request.

Examples of undeclared context include:

* ambient application state;
* hidden prompt text;
* provider defaults;
* undocumented session history;
* mutable global variables;
* operator assumptions;
* unrecorded tool availability.

Any context that materially affects canonical construction SHALL be represented in a versioned and traceable input artifact.

---

# 8. Canonical outputs

**Specification level:** Required observable behavior

SRE-000-OUTCOME-001

Every completed request-construction transaction SHALL produce exactly one of the following:

1. one `CanonicalStructuredRequest`; or
2. one `StructuredRequestFailureRecord`.

It SHALL NOT produce both as authoritative outcomes for the same transaction.

It SHALL NOT produce neither.

```text
Completed Construction Transaction
              │
              ├── success ──► exactly one CanonicalStructuredRequest
              │
              └── failure ──► exactly one StructuredRequestFailureRecord
```

Non-authoritative diagnostic material MAY accompany either outcome.

Diagnostic material SHALL NOT replace the required canonical outcome.

# 9. Authority boundary

**Specification level:** Constitutional concept

The Structured Request Engine possesses only the authority required to transform admitted source and proposal artifacts into a canonical request representation or explicit failure record.

Its authority is:

* representational;
* structural;
* normalizing;
* validating;
* ordering;
* provenance-preserving;
* identity-producing within its own artifact domain.

Its authority is not:

* governmental;
* legal;
* organizational;
* policy-setting;
* safety-authorizing;
* provider-selecting;
* execution-granting;
* credential-granting;
* release-granting.

The engine’s authority terminates at issuance of its canonical output and handoff package.

---

# 10. One-authority-per-transformation principle

**Specification level:** Constitutional concept

SRE-000-TRANSFORM-001

Every canonical transformation SHALL have exactly one owning authority within the contract architecture.

Examples include:

| Transformation                   | Owning authority                            |
| -------------------------------- | ------------------------------------------- |
| Source intake recording          | Source intake boundary                      |
| Interpretation proposal creation | Interpreter implementation                  |
| Proposal admission               | Interpretation boundary                     |
| Proposal reconciliation          | Structured Request Engine                   |
| Representation normalization     | Structured Request Engine                   |
| Canonical ordering               | Structured Request Engine                   |
| Structural validation            | Structured Request Engine                   |
| Contradiction evaluation         | Structured Request Engine                   |
| Canonical request construction   | Structured Request Engine                   |
| Request identity issuance        | Structured Request Engine identity boundary |
| Authorization                    | External downstream authority               |
| Generation-envelope issuance     | Authorized downstream issuer                |
| Provider invocation              | External runtime                            |
| Output release                   | External release authority                  |

A transformation authority SHALL NOT silently perform the work of an adjacent authority.

An implementation MAY place multiple authorities within one process, but their artifact boundaries and responsibilities SHALL remain explicit.

---

# 11. Authority monotonicity

**Specification level:** Constitutional concept

SRE-000-AUTH-004

As an artifact moves through the Structured Request Engine lifecycle, its representational precision MAY increase.

Its execution authority SHALL NOT increase.

The following shall be prohibited:

```text
Source request
    ↓ normalization
More permission

Interpretation proposal
    ↓ validation
Trusted authority

Capability requirement
    ↓ canonicalization
Tool access

Canonical request
    ↓ serialization
Generation authority
```

Canonical processing may refine representation.

It may not manufacture permission.

# 14. Relationship to interpreters

**Specification level:** Logical artifact semantics

An interpreter is an external or caller-supplied component that proposes structured meaning.

Possible interpreters include:

* deterministic parsers;
* form mappers;
* rules engines;
* symbolic systems;
* language models;
* human-authored adapters;
* application-specific extractors.

The Structured Request Engine SHALL remain usable without a model-based interpreter.

## 14.1 Interpreter output status

Every interpreter output SHALL be classified as a proposal.

An interpretation proposal SHALL include sufficient metadata to establish:

* interpreter identity;
* interpreter version;
* proposal identity;
* source scope;
* proposal status;
* completion status;
* evidence references;
* declared assumptions;
* declared uncertainty;
* applicable bounds.

## 14.2 Interpreter prohibitions

An interpreter SHALL NOT:

* issue a canonical request;
* decide downstream policy;
* grant execution authority;
* choose tools on behalf of downstream governance;
* suppress ambiguity without representation;
* claim source evidence that does not exist;
* redefine contract semantics.

## 14.3 Nondeterministic interpreters

An interpreter MAY be nondeterministic.

The contract series SHALL define determinism beginning from admitted, fixed interpretation proposals and associated fixed inputs.

Equivalent engine input sets under equivalent versions and profiles SHALL produce equivalent canonical outputs.

# 15. Relationship to downstream authority

**Specification level:** Constitutional concept

A downstream authority receives a canonical request for evaluation.

It may determine whether to:

* accept;
* reject;
* defer;
* restrict;
* request clarification;
* transform the request into another authorized artifact.

The downstream authority SHALL be responsible for its own:

* policy rules;
* identity checks;
* capability checks;
* permission checks;
* safety checks;
* resource checks;
* execution conditions;
* release conditions.

The Structured Request Engine SHALL NOT preempt those decisions.

A downstream authority MAY reject a structurally valid canonical request.

A downstream authority MAY accept only part of a request.

A downstream authority MAY require clarification even when the engine classified the request as canonically issuable.

---

# 16. Relationship to Generation-Stack

**Specification level:** Constitutional concept

SRE-000-GEN-001

Generation-Stack SHALL remain downstream of an authorized generation artifact.

The Structured Request Engine SHALL NOT directly provide Generation-Stack with sufficient authority to begin generation.

The required conceptual sequence is:

```text
CanonicalStructuredRequest
        │
        ▼
Authority evaluation
        │
        ▼
Authority-produced GenerationEnvelope
        │
        ▼
Generation-Stack
```

The following shortcut SHALL be prohibited:

```text
CanonicalStructuredRequest
        │
        ▼
Generation-Stack
```

unless an external authorized boundary has explicitly performed the required transformation and the artifact identity reflects that transformation.

Generation-Stack SHALL NOT be made a required dependency of the Structured Request Engine.

# 17. Relationship to provider systems

**Specification level:** Constitutional concept

SRE-000-PROVIDER-001

The Structured Request Engine SHALL remain provider-neutral.

It SHALL NOT require:

* a particular model vendor;
* a particular API;
* a local model;
* a remote model;
* a particular transport;
* a particular generation stack;
* a particular tool framework.

Provider-specific transport SHALL remain outside the canonical engine core.

An optional seam MAY define a neutral interpreter interface.

Concrete provider implementations SHALL live outside the core authority boundary unless a later repository-level implementation specification establishes a separate adapter package without changing this contract.
