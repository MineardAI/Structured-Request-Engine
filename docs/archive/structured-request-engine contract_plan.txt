# 1. Purpose

This document defines the planning framework for the Structured Request Engine contract series.

It establishes:

* the purpose of the contract series;
* the project’s architectural and authority boundaries;
* the proposed contract inventory;
* the dependency order between contracts;
* the canonical artifact families that require definition;
* the review and adoption process;
* the conditions that must be satisfied before implementation planning begins;
* the relationship between contract planning, implementation planning, and Codex implementation.

This document does not itself define the complete runtime behavior of the Structured Request Engine.

It governs how those definitions will be created, reviewed, adopted, and transferred into implementation planning.

---

# 2. Project identity

The Structured Request Engine is the portable request-structuring boundary for Mineard AI systems.

Its role is:

> Convert source input into a canonical, provenance-preserving, machine-readable representation of what was requested without granting execution authority, selecting providers, planning work, invoking tools, producing an answer, or releasing output.

The engine may identify and represent:

* requested objectives;
* declared constraints;
* capability requirements;
* source references;
* ambiguities;
* assumptions;
* uncertainty;
* interpretation evidence;
* relationships among request elements;
* provenance and lineage.

The engine may not transform those descriptions into permission to act.

The fundamental project distinction is:

```text
CanonicalStructuredRequest
        ≠ AuthorizedRequest
        ≠ GenerationEnvelope
        ≠ ExecutionPlan
        ≠ GeneratedOutput
```

Canonicalization records a request in a stable form.

Canonicalization is not authorization.

# 3. Architectural position

The Structured Request Engine occupies the boundary between source submission and downstream authority evaluation.

```text
Human / Application / API Input
                │
                ▼
      Structured Request Engine
                │
                ▼
      CanonicalStructuredRequest
                │
                ▼
        Authority / Governance
        IBOS, SACS, or another
        authorized runtime boundary
                │
                ▼
         GenerationEnvelope
                │
                ▼
         Generation-Stack
                │
                ▼
        Caller-supplied Provider
```

The Structured Request Engine belongs before:

* authority evaluation;
* governance decisions;
* planning;
* generation;
* provider invocation;
* tool execution;
* output release.

It does not belong inside:

* Generation-Stack;
* IBOS-Lite;
* Local-Model-Provider;
* SACS;
* Persona Forge;
* a concrete model provider;
* a tool runtime;
* an execution system.

Those systems may consume or reference its output, but they must not redefine or silently alter its canonical request contracts.

# 4. Contract-program objective

The contract program shall produce a complete normative specification from which the Structured Request Engine can be implemented without requiring the implementer to invent architectural meaning.

The contract program must define:

1. what enters the system;
2. what artifacts may be constructed;
3. which artifacts are proposals rather than authoritative records;
4. which transformations are deterministic;
5. which component owns each transformation;
6. how source evidence is preserved;
7. how ambiguities and assumptions are represented;
8. how objectives and constraints are represented;
9. how capability requirements remain distinct from authority;
10. how conflicting proposals are handled;
11. how canonical ordering is established;
12. how structural validity is evaluated;
13. how deterministic identity is calculated;
14. how failures are represented;
15. what may be handed to downstream authority;
16. what the downstream handoff does not imply.

The contract program shall also distinguish among four levels of specification:

1. **Constitutional concepts** — semantic or authority distinctions that every conforming implementation must preserve.
2. **Logical artifacts** — normative information groupings that must be representable but need not become standalone runtime objects or Rust types.
3. **Required runtime artifacts** — inspectable runtime values that every conforming implementation must construct, consume, or emit.
4. **Implementation conveniences** — internal structures that an implementation may use but that are not required by the contracts.

A named concept in a contract shall not automatically require a dedicated Rust type, module, file, state object, or serialized artifact.

Each contract shall classify its major concepts and artifacts before reaching Candidate status.

# 5. Contract-program principles

The complete contract series shall preserve the following principles.

## 5.1 Canonicalization is not authorization

A `CanonicalStructuredRequest` represents what was requested in a deterministic machine-readable form.

It does not mean that the request is:

* approved;
* permitted;
* safe;
* feasible;
* funded;
* authenticated;
* executable;
* schedulable;
* supported by available capabilities.

## 5.2 Interpretation is not authority

An interpreter may be:

* a language model;
* a rules engine;
* a form parser;
* an application adapter;
* a symbolic system;
* a manually supplied implementation.

Its output is an interpretation proposal.

Interpretation proposals are untrusted inputs to deterministic request construction.

No interpreter may independently issue a canonical request.

## 5.3 Complete representation is not complete understanding

A request may be canonically complete while retaining unresolved ambiguity.

The engine shall not invent certainty merely to produce a structurally complete artifact.

```text
Complete representation
        ≠
Complete understanding
```

## 5.4 Capability requirement is not capability authority

A capability requirement describes what may be needed to satisfy a request.

It does not establish:

* that the capability exists;
* that a connector is configured;
* that credentials are available;
* that access is permitted;
* that a specific provider or tool should be selected;
* that execution may begin.

## 5.5 Evidence must remain traceable

Interpreted request elements must retain explicit evidence linking them to source material or another declared origin.

The engine must distinguish:

* source-explicit content;
* interpreter-inferred content;
* application-supplied content;
* referenced-artifact content;
* normalized representation.

## 5.6 Determinism begins after interpretation input

An external interpreter may be nondeterministic.

Once interpretation proposals and their evidence enter the deterministic engine boundary, all subsequent processing covered by the contracts must produce reproducible results for equivalent inputs, versions, registries, and configurations.

## 5.7 Authority may not expand through representation

No stage may convert:

* a requested action into permission;
* a capability need into access;
* an inferred objective into user consent;
* an ambiguity into a guessed fact;
* an interpreter suggestion into policy;
* a canonical request into a generation envelope.

## 5.8 Semantic identity and submission identity are distinct

Multiple submissions may have different event identities while representing the same canonical request semantics.

The contracts shall distinguish at least:

```text
Submission identity
    Identifies a particular intake event.

Canonical request identity
    Identifies the canonical semantic representation.

Source identity
    Identifies the supplied source material.

Interpretation identity
    Identifies a particular interpretation proposal.
```

## 5.9 Meaning shall remain distinct from implementation form

The contract series shall define constitutional meaning and required observable behavior.

It shall not prescribe a particular internal implementation unless that implementation detail is necessary for:

* deterministic behavior;
* interoperability;
* canonical identity;
* serialization compatibility;
* authority preservation;
* externally observable conformance.

The same logical artifact may be implemented as:

* a dedicated runtime type;
* fields within a larger artifact;
* an internal validated view;
* a generated representation;
* another equivalent structure.

Implementation equivalence is permitted only when the required semantics, provenance, determinism, and authority boundaries remain observable and testable.

# 7. Planned canonical lifecycle

The contract series shall refine the following lifecycle:

```text
Source Submission
        │
        ▼
Source Intake Record
        │
        ▼
Interpretation Request
        │
        ▼
Untrusted Interpretation Proposal
        │
        ▼
Interpretation Evidence Validation
        │
        ▼
Proposal Reconciliation
        │
        ▼
Representation Normalization
        │
        ▼
Constraint and Contradiction Evaluation
        │
        ▼
Canonical Ordering
        │
        ▼
Structural Validation
        │
        ▼
Canonical Request Construction
        │
        ├── success ──► CanonicalStructuredRequest
        │
        └── failure ──► StructuredRequestFailureRecord
```

The successful output may be submitted to a separate authority boundary.

```text
CanonicalStructuredRequest
        │
        ▼
Downstream authority evaluation
        │
        ├── accepted within bounded authority
        ├── rejected
        ├── deferred
        ├── restricted
        └── clarification required
```

These downstream decisions are outside the Structured Request Engine.

# 8. Prototype feedback gate

After Contracts 000 through 005 reach at least Candidate status, the project may construct a minimal walking-skeleton prototype.

The prototype exists only to test whether the constitutional distinctions survive contact with implementation.

The prototype shall exercise:

```text
Source input
    ↓
Interpretation proposal
    ↓
Minimal deterministic canonicalization
    ↓
CanonicalStructuredRequest
    ↓
Non-authorizing handoff
```

The prototype shall be classified as:

* experimental;
* non-production;
* non-canonical;
* non-conforming until evaluated;
* replaceable without compatibility guarantees.

The prototype shall not:

* establish the final public API;
* establish the final crate structure;
* establish the final serialization format;
* become the de facto contract;
* invoke providers for answer generation;
* perform policy authorization;
* perform planning;
* perform execution;
* issue a `GenerationEnvelope`;
* introduce compatibility commitments.

Its outputs shall be treated as architectural evidence, not as canonical project artifacts.

Prototype findings may result in amendments to Contracts 000 through 005.

Any such amendment shall be explicit, versioned, reviewed, and recorded before later contracts rely on the changed behavior.

# 9. Contract-family organization

The planned contracts are divided into four families.

## 9.1 Constitutional contracts

These establish project identity, authority, source boundaries, and the interpretation boundary.

## 9.2 Request-artifact contracts

These establish the ontology used to represent what was requested.

## 9.3 Deterministic-processing contracts

These establish how proposals are transformed into a canonical request.

## 9.4 Issuance and handoff contracts

These establish canonical construction, deterministic identity, failure issuance, and downstream transfer.

# 10. Proposed contract inventory

The numbering below is a planning baseline.

Contract numbers and titles become frozen only when this planning record is adopted.

The separation of normative contracts does not require equivalent implementation decomposition.

Multiple contracts may map to one implementation subsystem, crate, module, or validation pipeline.

In particular, evidence, provenance, identity, and serialization may remain separate normative concerns while being implemented through a shared subsystem.
