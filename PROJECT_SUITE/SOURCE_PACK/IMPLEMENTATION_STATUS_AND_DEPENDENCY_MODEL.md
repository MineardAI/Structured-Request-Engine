# Implementation Status and Dependency Model

This vocabulary supports progressive implementation tracking. It does not change contract status, create runtime authority, or require one module or crate per contract.

## Implementation status vocabulary

| Status | Meaning |
| --- | --- |
| `Not Started` | No implementation mapping or implementation activity has been evidenced. |
| `Extracted` | Requirements have been extracted from identified governing sources. |
| `Mapped` | Requirements and boundaries are mapped to inspectable surfaces, but implementation has not begun. |
| `Decision Blocked` | Work cannot proceed without a named authority or unresolved implementation decision. |
| `Implementable` | A bounded slice has sufficient mapped decisions and dependencies to begin without semantic invention. |
| `In Progress` | Authorized bounded implementation work is underway. |
| `Implemented` | The mapped surface exists, but verification is incomplete. |
| `Verified` | Inspectable evidence demonstrates the mapped behavior or prohibition for the declared scope. |
| `Conditionally Complete` | The slice is verified only within explicit limitations recorded in traceability and dependencies. |
| `Deferred by Authority` | Work is intentionally postponed because a governing authority or later phase owns the unresolved question; this is not a failure. |
| `Non-Conforming` | An identified requirement or authority boundary is violated. |
| `Superseded Implementation Mapping` | A prior mapping is retained for history but replaced by a later explicitly identified mapping. |

Contract readiness is not implementation status. `Implemented` is not `Verified`; `Verified` is not constitutionally adopted. `Conditionally Complete` requires explicit limitations. `Deferred by Authority` is not a failure. `Non-Conforming` must name the violated requirement or boundary.

Before resolving a Decision Register entry, determine whether it affects externally observable constitutional behavior. If it does, implement only behavior already defined by the governing contract, adopted architecture, or explicitly authorized versioned profile or policy. Do not invent externally observable semantics. Resolve only internal implementation mechanisms required for the authorized slice.

Different internal algorithms or mechanisms are permitted only when they produce the required equivalent observable result under the same declared constitutional inputs and version context. An unresolved observable semantic issue is `Decision Blocked` or `Deferred by Authority`, not an implementation convenience decision.

## Dependency classes

| Class | Meaning |
| --- | --- |
| **Normative Dependency** | Another contract or architecture governs the meaning or authority required by the source slice. |
| **Implementation Dependency** | Shared code, infrastructure, profile resolution, registry support, identity primitives, or persistence must exist first. |
| **Evidence Dependency** | Closure requires tests, fixtures, mappings, or evidence generated by another slice. |

Normative dependency does not automatically require one crate or module per contract. Co-location is permitted only when inputs, outputs, authority, and publication boundaries remain inspectable.

## Required dependency record

Each dependency record must contain:

| Field | Required content |
| --- | --- |
| `dependency_id` | Stable dependency identifier. |
| `dependency_class` | `Normative`, `Implementation`, or `Evidence`. |
| `source` | Slice or artifact that depends on the target. |
| `target` | Governing source, artifact, surface, or evidence target. |
| `reason` | Why the dependency exists. |
| `blocking_status` | `Blocking` or `Non-Blocking`, with rationale. |
| `completion_evidence` | Inspectable evidence required to close it. |
| `authority_boundary` | What the dependency does and does not authorize. |
| `consequence_if_unmet` | Resulting status or limitation if unresolved. |

## Boundary rules

- A normative dependency may constrain meaning but may not silently transfer publication authority.
- An implementation dependency may be replaced by another surface if traceability and behavior remain explicit.
- An evidence dependency is not satisfied by an assertion that a test should exist.
- Missing evidence keeps a slice below `Verified`.
- A valid unresolved or negative contract state must not be recorded as operation failure solely because it is non-success.
