# Implementation Traceability Schema

This schema is a supporting traceability control, not a second implementation plan. It records how later implementation slices demonstrate conformance without changing normative meaning or contract status.

## Required chain

```text
Normative Requirement ID
        ->
Implementation Decision
        ->
Implementation Surface
        ->
Verification Method
        ->
Test / Fixture / Conformance Vector
        ->
Evidence Record
        ->
Disposition
```

## Reusable row schema

| Field | Required content |
| --- | --- |
| `requirement_id` | Stable identifier from the governing contract or architecture. |
| `source_document` | Exact source filename. |
| `source_version` | Exact source version/status snapshot. |
| `source_clause` | Exact clause or requirement identifier. |
| `requirement_summary` | Faithful concise statement of the requirement. |
| `constitutional_act` | Bounded act owned by the source contract. |
| `owning_authority` | Authority that may publish or commit the governed artifact. |
| `implementation_decision_id` | Decision-register or formal decision identifier; unresolved decisions remain explicit. |
| `behavior_classification` | `Internal Mechanism`, `Externally Observable Behavior`, or `Mixed — Requires Bounded Decomposition`. |
| `observable_effect` | Externally visible artifact, state, identity, interoperability, replay, or conformance effect. |
| `governing_source_required` | Contract, adopted architecture, authorized versioned profile/policy, or formally recorded repair required for the observable behavior. |
| `implementation_resolution_permitted` | Internal mechanisms that may vary while preserving the governed observable result. |
| `required_decomposition` | Separation of observable semantics from internal realization for mixed decisions. |
| `implementation_surface` | Code, schema, adapter, storage, or other inspectable surface. |
| `artifact_or_behavior` | Principal artifact or observable behavior addressed. |
| `verification_method` | Test, fixture, static check, inspection, replay, or conformance method. |
| `test_or_fixture` | Exact test, fixture, vector, or named evidence source. |
| `evidence_location` | Inspectable path, record, or output location. |
| `implementation_status` | Value from `IMPLEMENTATION_STATUS_AND_DEPENDENCY_MODEL.md`. |
| `conformance_disposition` | `Conforming`, `Non-Conforming`, `Deferred`, `Not Applicable`, or repository-equivalent with rationale. |
| `declared_limitation` | Explicit boundary, missing authority, or incomplete scope. |
| `deferred_dependency` | Named dependency when status is deferred or blocked. |
| `notes` | Additional trace context without normative invention. |

## Rules

- One requirement may map to multiple implementation surfaces and tests; every mapping remains explicit.
- One code surface may satisfy multiple requirements only when each requirement mapping is separately recorded.
- No requirement is `Verified` without inspectable evidence.
- `Not Applicable` requires a contract-grounded explanation.
- `Deferred` requires a named dependency and authority boundary.
- Implementation convenience cannot silently satisfy or redefine normative semantics.
- Negative prohibitions receive explicit tests or static verification where feasible.
- Valid unresolved outcomes are tested separately from operation failures.
- Atomic success/failure behavior receives explicit conformance evidence.
- Exact source versions are retained in every row.
- Before resolving a Decision Register entry, determine whether it affects externally observable constitutional behavior. If it does, implement only behavior already defined by the governing contract, adopted architecture, or explicitly authorized versioned profile or policy. Do not invent externally observable semantics. Resolve only internal implementation mechanisms required for the authorized slice.
- Different algorithms or mechanisms are permitted only when they produce the required equivalent observable result under the same declared constitutional inputs and version context.
- This schema does not require one crate, module, or service per contract.
